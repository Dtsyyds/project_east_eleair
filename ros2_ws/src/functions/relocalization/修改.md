## 两种模式

配置仍使用 `/**.ros__parameters.locate_in_prior_map`，任务中途不切换模式。

| 模式 | 配准节点 | `map → camera_init` |
|---|---|---|
| `false`：直接建图 | 存活但不执行配准 | 平移 `(0,0,0)`，四元数 `(0,0,0,1)`；`map` 与本次局部建图坐标系重合 |
| `true`：重定位 | 配准后经 `/fast_livo2/set_initial_pose` 提交初值，确认接受后空闲存活 | FAST-LIVO 完成先验初始化后发布 `/fast_livo2/initial_map_pose`，TF 节点使用最终对齐结果 |

重定位没有成功时不会发布零变换兜底。TF 存在也不等于建图已经就绪，上位机仍检查有效跟踪、里程计和重定位初始化证据。

## 重定位成功后提前停止修复（2026-11-11）

失败会话 `20261111_012047_710dbbdd3d6a` 的完整日志表明：GICP 已成功收敛，FAST-LIVO 已接受初值，但求解器随后主动 `rclcpp::shutdown()`，以 0 退出；统一 launch 按“三个核心节点任一退出即收尾”的规则关闭整组算法，此时 IMU 初始化仅到 3.3%。这次故障发生在初值被接受之后，并非配准失败。

现在确认接受初值后进入空闲状态，不再主动退出：取消交付超时看门狗、释放点云及手动初值订阅、释放服务客户端与请求。保留 `/icp_result` 的持久化发布者，便于后连接的上位机读取固定初值。FAST-LIVO 独立继续完成 IMU 与先验初始化、发布最终对齐位姿并输出里程计。接受初值不等于初始化完成，仍需保持静止直到就绪。

初值被拒绝、交付超时、地图加载失败仍按异常退出处理；统一 launch 的三节点故障联动规则不变。此次未修改配准精度参数、FAST-LIVO 算法或上位机业务代码。

## 编译与生效

运行时使用 `ros2_ws/install/` 下的 launch 和程序，源码修改后需要重新安装。本机已使用现有 CMake 构建目录编译并安装 `relocalization`：

```bash
source deploy/env.sh s100p
cmake --build ros2_ws/build/relocalization --parallel 2
cmake --install ros2_ws/build/relocalization
```

安装已同步上述 C++ 修改及两个 launch；未改动的 FAST-LIVO 不需要重编译。已有整机服务需正常退出并等待保存完成，再用原命令 `bash system_websocket/run_robot.sh` 启动，才能加载上位机 Python 改动。本次不自动停止现场服务。

本次追加的“重定位成功后提前停止”修复仅涉及算法程序，已重新编译安装：下次从页面启动算法任务即使用新程序，无需为此项修复重启上位机服务。若仍有活动任务，先从页面正常停止并等待收尾，再启动；不要额外手动启动算法或驱动。
