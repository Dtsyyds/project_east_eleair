# 2026-11-06 鱼眼无回传与 D405 帧率排查

## 结论

鱼眼在最近一次整机启动时没有被系统识别，驱动初始化失败并退出，因而没有图像可向上位机发送。新旧 D405 模型网络规模和推理后端相同，同图交替测试未测到新权重的神经网络推理变慢。现场低帧率与丢线后的候选搜索、并行运行开销有关；换模前旧权重也已有低于 6 FPS 的记录。

未修改运行代码、默认配置或模型权重。测试只运行相机、通信桥和被动视觉节点，使用独立 ROS 域 178，不启动底盘控制；结束后相关测试进程均已退出。

- `.runtime/s100p/web_console/hardware.log` 的 17:35 启动记录：`fisheye stable device selection matched 0 paths for 'icSpring_icspring_camera_20240307110322'`，随后 `fisheye_camera_node` 以退出码 1 结束。原日志已复制到本次产物目录的 `hardware_before.log`。
- 排查时 `/dev/v4l/by-id` 只有 RealSense D405；`lsusb` 有 D405、MindVision、Hub 和串口转换器，没有 icSpring 鱼眼设备。
- `robot_all.yaml` 已启用 `start_fisheye: true`；桥接配置订阅 `/camera/fisheye/image_raw`。当前直接断点在设备发现/驱动初始化。
- 驱动在 `FisheyeCameraNode.__init__` 调用 `resolve_device()`，零匹配直接抛异常。重连线程此时尚未建立，且 bringup 没有为该节点配置 respawn。因此启动时缺设备后，随后插上也不会自动恢复这个已经退出的进程。

目前无法仅靠软件区分线缆、供电、Hub、物理断开或设备故障。应先恢复 icSpring 的 USB 枚举和对应 `*-video-index0` 路径，再重启鱼眼节点/相机后台，并验证 ROS 图像和网页预览。不能把 `/dev/video0` 强行指定为鱼眼：当前它属于 D405。尚未验证鱼眼恢复出图，也未宣称远端网页链路验收完成。

启用真实 D405、1920×1200/10 Hz 工业相机和通信桥后，再运行同样的同图测试：旧/新推理平均 95.66/94.72 ms，整体 147.17/128.63 ms。测得并行后台增加约 7–9 ms 整体开销，但这不是完整整机负载，不能解释历史 40–70 ms 增量的全部来源。

## 真实相机短时对照

同一启动周期，旧、新权重分别运行 20 秒，其他相机和桥接设置相同；顺序执行而非逐帧同图，场景/曝光变化未受控，因此作为现场复现与阶段定位，不能作为严格精度对比。

| 指标 | 旧模型 | 新模型 |
| --- | ---: | ---: |
| 处理 FPS | 5.91 | 5.44 |
| 已处理帧 | 119 | 109 |
| LOST 帧 | 95 | 109 |
| 平均推理阶段 ms | 96.65 | 97.88 |
| 平均解码 ms | 17.87 | 17.14 |
| 平均恢复候选/状态处理 ms | 47.45 | 61.87 |
| 平均算法整体 ms | 163.57 | 178.40 |

本次约 14.8 ms 的整体差异主要落在恢复候选阶段，网络推理只差约 1.2 ms。`recovery.py:190` 在手动选择模式或当前 2D 输出无效时调用 `propose()`；后者最多做 6 轮路径搜索以产生最多 3 条候选。正常自动识别成功时跳过该搜索。离线正常帧的恢复状态处理约 0.4 ms，丢线帧约 54–62 ms。

7 FPS 每帧预算约 143 ms。历史正常识别的 124 ms 算法时间加通信/调度开销可以做到 7.57 FPS；当前丢线时约 178 ms 算法时间，加回调与调度后约 5.44 FPS，与实测一致。

## 处理方向和边界

1. 鱼眼先排除物理连接/供电/枚举问题，再重启驱动验证。启动缺设备时保持节点存活并重试、诊断显示最近帧年龄，属于可后续实施的软件恢复改进，不能代替恢复硬件连接。
2. 帧率应优先剖析并优化恢复候选搜索，以及完整整机负载下的推理耗时；不能单凭换回旧权重保证 7 FPS。本次没有减少搜索、放宽质量门槛或更改目标选择行为。
3. 对正常识别仍只有约 5 FPS 的整机会话，需完整负载下补充逐阶段耗时、CPU 调度/竞争记录，当前只能确认差异存在且早于换模，不能指定未经测量的单个进程为唯一根因。
