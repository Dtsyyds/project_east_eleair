## 日常测试：整个工程上位机（包含 SLAM，优先使用）

如果之前启动了独立测试的雷达、IMU 转换或 SLAM 服务，先在其原终端按 Ctrl+C 并等待退出，避免重复启动传感器或占用 `8082`。整套入口会启动原 robot、camera、gateway 和独立 slam 服务，传感器由原整套启动链负责，无须另外运行雷达、IMU 或算法命令。

查看计划并做静态预检：

```bash
cd /media/mcap_data/project_east_eleair_refactor
bash system_websocket/run_robot.sh --slam --plan
bash system_websocket/run_robot.sh --slam --check
```

预检通过后启动整套服务：

```bash
bash system_websocket/run_robot.sh --slam
```

浏览器打开 `http://192.168.127.10:8080/` 或 `http://192.168.1.148:8080/`，进入“定位与建图”。此时也可以直接访问同一设备的 `8082`，两种入口操作的是同一个 SLAM 会话。

先检查原有实时巡检、采集任务和底盘页面，再测试 SLAM 的启动、点云、停止保存。以上命令沿用默认循迹预览模式，不加 `--real`；SLAM 测试不要求实车循迹。退出时在启动终端按 Ctrl+C，等待保存和录制收尾完成。

只测试原整套上位机、不启动 SLAM 服务时使用：

```bash
cd /media/mcap_data/project_east_eleair_refactor
bash system_websocket/run_robot.sh --check
# 预检通过后执行：
bash system_websocket/run_robot.sh
```

两种模式默认 ROS 域均为 77。浏览器访问其他主机/IP 时，在对应启动命令追加 `--host 实际主机或IP`，多个地址重复传入；使用实时输入时不要向相同话题同时发布回放数据。

## 备用测试：独立 SLAM 上位机

从零启动时使用下面三个终端。若已有 `/livox/lidar` 的 CustomMsg 和 `/livox/imu` 的米制 IMU 输入，直接执行终端 C，不重复启动 A、B。独立测试不需要启动相机、底盘或整套巡检后台。

### 终端 A：雷达驱动

```bash
cd /media/mcap_data/project_east_eleair_refactor
source deploy/env.sh s100p
export ROS_DOMAIN_ID=77 ROS_LOCALHOST_ONLY=0

ros2 run livox_ros_driver2 livox_ros_driver2_node --ros-args \
  -p xfer_format:=1 -p multi_topic:=0 -p data_src:=0 \
  -p publish_freq:=10.0 -p output_data_type:=0 -p frame_id:=livox_frame \
  -p user_config_path:="$PWD/ros2_ws/src/drivers/livox_ros_driver2/config/MID360_config.json" \
  -r /livox/imu:=/livox/imu_raw
```

当前 `MID360_config.json` 配置雷达 IP 为 `192.168.2.3`、板端雷达网口 IP 为 `192.168.2.100`，须与实际网络一致；使用其他现场配置时替换 JSON 路径。

### 终端 B：IMU 单位转换

把 `/livox/imu_raw` 的加速度从 g 转为 `/livox/imu` 的 m/s²：

## 实现范围与独立性

- 独立页面和后台共用 `8082`，入口为 `system_websocket/run_slam.sh`。服务启动后空闲，网页启动请求才运行算法；直接建图、先验重定位后继续扩图共用现有算法入口。
- 功能主体、配置、协议和测试都在本目录；不导入 `inspection_runtime`、`inspection_operations`、`agv_bridge`，不复制算法、launch、基础 YAML 或整套主界面，不新增传感器驱动。
- 原主界面仅增加导航和 iframe 接入。整套启动器通过 `--slam` 可选启动同一个独立服务；不带参数的原启动计划保持不变。
- 每次生成独立运行配置及唯一输出目录，保存选项随本次会话锁定。停止与 Ctrl+C 先 SIGINT；算法内部宽限期 120 秒，后台清理预算 130 秒，整套 SLAM 退出预算 150 秒。
- 使用守护进程、生命周期管道及 Linux subreaper 清理本次子进程。SLAM 服务失败只记录一次，不结束整套其他模块，不自动重启算法，不广泛按进程名杀进程。
- 日志保存完整原始 stdout/stderr 和带时间/来源的合并日志；页面按游标分页读取。点云使用原始 PointCloud2 的实际坐标系，只做有界预览，不修改 ROS 消息和录包。

## 整套主界面周期性断连：网关调整与复测

现有 19:29 会话日志显示相机桥接进程存活，而本机网关连接反复建立/关闭。旧网关把所有方向的单次发送都限制为 250ms，并吞掉异常，不能从旧日志确认具体根因。本次先处理这个容易误断开的期限，并补齐诊断；需要现场复测才能确认此次周期性断连是否消失。

- `/ws/inspection`（包括 `/`、`/ws` 相机别名）的后台 → 浏览器发送期限改为 2 秒，允许图像发送短暂阻塞。
- 浏览器 → 后台的控制请求仍为 250ms；`/ws/robot` 两个方向都保持 250ms。未修改底盘控制租约、停车规则，也不重发或排队旧控制请求。
- 上游消息队列仍为 1，不增加无界缓存。客户端持续阻塞超过期限仍断开并清理对应上游。
- 心跳仍为 5 秒一次、等待 3 秒；新日志区分心跳超时和发送超时，先用实际证据判断是否需要另调心跳。
- `gateway.log` 每次连接/断开记录时间、连接编号、路由、方向、持续时间、关闭码、消息数量/字节数、最慢发送耗时及超过 250ms 的发送次数；不记录报文正文、Token、对端任意错误文本。
- 浏览器关闭原因改为具体分类，不再统一显示 `backend_closed_or_unavailable`。页面“设备与调试 → 验证日志”中的“连接关闭”也能看到对应原因。

修改后需要重启整套入口才生效：先在原启动终端按 Ctrl+C，等待保存和录制收尾，再执行本文开头的 `run_robot.sh --slam --check` 和 `run_robot.sh --slam`，浏览器 Ctrl+F5 刷新。此轮修改没有自动停止或重启现场进程。

## 20:10 现场反馈后的修正：解除预览堵塞引起的心跳超时

现场日志连续三次在约 8.4 秒出现 `upstream_heartbeat_timeout`，相机数据仍在接收，最慢下行发送为 665～952ms。20:10:25 的整套日志同时记录了退出收尾，因此该时刻底盘连接的 `1001` 关闭与前面的相机周期性心跳超时应分开判断。

此前只把相机发送期限从 250ms 调到 2s，未解除串行“读一条、发一条”结构的问题：发送受阻时不继续调用上游 recv，`websockets.legacy` 的 `max_queue=1` 队列满后暂停读取数据帧，排在后面的 Pong 也无法处理。即使后台已经回答 Ping，也可能在 5 秒发 Ping、再等 3 秒后被判超时。本轮对照测试专门复现这一机制。

本轮自动验证结果：**33 passed in 28.09s**，另有 6 条原 legacy API 弃用提示。真实回环 WebSocket 对照测试证明旧串行路径在服务端已回 Pong 时仍超时；修复路径通过多轮心跳，并在原 5 秒/3 秒参数下持续承受 20 多秒预览输入快于浏览器发送的拥塞，5 条模拟只读请求的回包完整且顺序一致。Python 编译和差异检查通过。测试未启动真实硬件，现场效果仍需按下文复测。

本轮修改仍仅位于 `tools/robot_gateway.py`、`tests/operations/test_robot_gateway.py` 和本记录：

- 相机上游独立持续读取，浏览器发送由另一协程处理，避免慢浏览器阻塞本机心跳读取。
- 只对现有 `tank_inspection_v2` 协议中、无 request_id、单一 payload、明确标记 `visualization_only=true` 的视频/雷达/涡流预览保留每路最新包。原消息原样转发，不修改时间戳、帧引用或像素数据。
- 响应、事件、状态、混合包、未知协议和二进制消息按 FIFO 优先发送，不做静默替换；浏览器发往后台的请求仍按原逻辑处理，不重放控制命令。
- 每连接待发送缓存上限 8 MiB，普通 FIFO 最多 64 条、预览最多 16 路；超限明确报 `inspection_queue_overflow` 并断开。仅用于显示的待发预览超过 2 秒时过期丢弃。以上限制不含当前传输包、解析临时对象和协议/TCP 自身缓冲。
- 心跳仍启用且保持原来的 5 秒/3 秒；不靠关闭心跳或无限拉长超时掩盖堵塞。底盘 `/ws/robot` 链路不改动。
- 每 5 秒记录 `inspection_flow`，可看 `received_messages`、`previews_replaced`、`previews_expired`、`queued_bytes`、`peak_queued_bytes` 等。连接记录新增 `downstream_policy: latest_preview`，用于确认已经加载本次版本。
- 慢链路下预览帧率会降低，以显示较新画面并保持响应；ROS 原始消息和 MCAP 数据不受预览替换影响。

复测仍使用本文开头的整套入口。先退出旧进程并等待收尾，再启动 `bash system_websocket/run_robot.sh --slam`；只需重新加载 Python 网关，无须为本次修改重新构建 ROS 包。浏览器 Ctrl+F5 后，观察 1～2 分钟，超过原先每 8.4 秒断开的周期，并查看 `gateway.log`：

- `connected` 应含 `downstream_policy: latest_preview`。
- 带宽不足时 `previews_replaced` 增加是主动淘汰旧预览，不代表采集丢包。
- 若仍出现心跳超时、发送超时或缓存溢出，保留对应 `disconnected` 及此前 `inspection_flow` 行，以进一步区分真实后台停顿与网络吞吐不足。

## SLAM 白页及“连接中 · 状态未知”修复

现场现象为 SLAM 页面白底、控件未应用主界面风格、一直停留初始连接文案。检查发现独立 HTTP 服务的资源响应头错误：`connection.respond()` 自动生成 `Content-Type: text/plain`，而 `websockets.Headers` 的赋值语义是追加，不是普通字典的覆盖。原实现又追加一次 HTML/CSS/JS 类型，导致每个响应存在两个 Content-Type。配合 `X-Content-Type-Options: nosniff`，部分浏览器会拒绝应用样式或执行脚本。之前 Firefox 验证没有暴露这项兼容性问题，普通 dict 模拟响应头的单元测试也没有覆盖它。

“连接中 · 状态未知”原本是 HTML 的静态初始文案；脚本未执行时不会建立 WebSocket，也无法更新文字。这不表示正在初始化建图。加载正常时，服务未运行算法应显示空闲；独立 HTTP/WS 服务连接和真实传感器输入检查是不同阶段。

本轮改动：

- `apps/web_console_slam/slam_console/server.py`：先删除默认 Content-Type，再设置且只设置一个正确 MIME；保留 `nosniff` 和 `no-store`。CSP 明确允许实际访问主机的 `ws://主机:8082`，避免依赖浏览器对 `connect-src self` 的 WebSocket 解释差异。
- `apps/web_console_slam/index.html`、`console.js`：为资源添加版本标识；静态初始文字改为“正在加载页面资源…”，脚本实际运行后才显示连接阶段；JavaScript 被禁用时显示说明。已有工业深色面板、字体、按钮、徽标、日志和点云样式继续与整套主界面一致，保留独立资源避免运行依赖其他网页服务。
- `apps/web_console_chassis_tracking/slam_embed.js`、`index.html`：更新接入脚本版本；页面迟迟不就绪时同时提示检查服务和资源加载，不再只提示缺少 `--slam`。
- `apps/web_console_slam/tests/test_transport.py`：使用真实 WebSocket 库响应头语义代替普通字典；验证实际 HTTP 返回的 HTML/CSS/JS 类型唯一且正确，包含带版本查询参数的请求。
- 本文件：记录白页原因、修正、验证与生效方式。网关预览分流及心跳修正保留，本轮不更改网络转发和算法逻辑。

生效方式：退出原整套入口并等待收尾，再使用本文开头的 `run_robot.sh --slam` 命令重新启动，然后在浏览器 Ctrl+F5。此次必须重新启动后台以加载修复后的 HTTP 响应代码，单独刷新页面不能修正仍在运行的旧进程；无须重新构建 ROS。

本轮验证：`SLAM_BROWSER_TEST=1 python3 -m pytest apps/web_console_slam/tests/test_transport.py apps/web_console_slam/tests/test_browser.py -q`，结果 **3 passed in 7.80s**。覆盖真实 HTTP 资源类型、WebSocket 连接与状态查询、Firefox 直连及整套嵌入、主题色一致、桌面和窄屏布局。已检查更新后的桌面截图，SLAM 面板、按钮和日志区均呈现与主界面一致的深色风格。未启动真实硬件，未进行 Chrome/Edge 实机验证；无头 Firefox 的 WebGL 限制仍如上文所述。
